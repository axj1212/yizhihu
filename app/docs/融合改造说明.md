# 两套项目代码融合改造说明

## 一、融合对象

| | 项目 A：medical-followup（医智呼随访） | 项目 B：ai-calling-plat（企业级智能外呼） |
|---|---|---|
| 定位 | 医疗随访业务系统：患者、随访任务、网页对话、风险评估、医生工单 | 通用外呼平台：线路、话术、名单、任务调度、会话、录音转写、质检 |
| 技术栈 | FastAPI + SQLAlchemy + SQLite + Vue3，LLM(agnes-3.0-flash) + RAG(bge-small-zh) | FastAPI + PostgreSQL + Vue3 + usip(SIP)，Docker Compose |
| 领域模型 | Patient / FollowTask / ConversationSession / RiskAssessment / DoctorTicket / PlanningCase | Trunk / Script / Contact / Task+Run / Session / Recording / QC |
| 强项 | 医疗语义、计划生成与确认、风险与工单闭环、知识库引用 | 外呼执行链路：线路管理、话术节点、任务批次、通话与转写追踪 |
| 短板 | 随访触达只停留在"网页会话"，没有真实电话外呼 | 无任何医疗业务语义，话术面向营销外呼 |

## 二、融合策略

1. **以 A 的领域模型为主干**：患者、随访计划、风险、工单直接吸收（含状态机、乐观锁、计划确认等工程化设计）。
2. **以 B 的外呼链路为执行引擎**：吸收其 Trunk（线路）、Script（话术模板/节点）、Task+Run（任务与批次）、Session/Recording（通话与转写）概念，替换 PostgreSQL 为 SQLite（单机可跑、答辩可演示），usip SIP 通道替换为阿里云语音双呼适配器（`providers/aliyun.py`，实现 dyvmsapi V3 签名）。
3. **消除双份患者表**：B 的 Contact 与 A 的 Patient 合并为同一 `patient` 表，外呼任务直接引用患者档案，避免两套系统对同一病人两份数据。
4. **话术从"静态模板"升级为"医生编排 + 大模型生成 + 医生审核"**：病种方案（Protocol）保存阶段、提问、追问分支、红旗；AI 可按病种/出院天数重写话术，进入 reviewing 状态，医生发布后才可生成计划。
5. **保留可演示性与可扩展性**：演练模式（simulator）与真实模式（阿里云）共用同一条「任务 → 通话 → 转写 → 结构化 → 风险 → 工单」管线，切换只需改线路配置。

## 三、数据模型映射

| 融合后模型 | 来自 A | 来自 B | 说明 |
|---|---|---|---|
| Protocol（病种方案） | PlanningCase/FollowTask.follow_plan | Script（话术版本/节点） | 阶段化话术模板 + 医生审核状态机 |
| Patient | PatientRecord | Contact | 单一患者主数据，含 HIS 导入来源 |
| Plan / Stage | FollowTask + follow_plan | Task 的批次概念 | 计划固化为不可变 Stage 快照 |
| CallTask | ConversationSession（触发来源） | Task/Run/Session | 外呼任务：排期、重拨、线路、录音 |
| CallResult | RiskAssessment + collected_information | 会话转写/质检结构化 | 大模型结构化抽取 + 规则风险分级 |
| Ticket | DoctorTicket | QC 工单概念 | 四级风险 SLA 处置闭环 |
| CallLine | — | Trunk（SIP/网关） | 阿里云语音双呼 + 白名单 |

## 四、业务规则落点（来自医生审定稿）

- 随访分级：稳定 7/30/90 天；高危 3 天首访、每 14 天一次 → `plan_service.stage_offsets`
- 未接通：30 分钟重拨 → 次日同时段 → 连续 5 次转失联 → `call_service._after_no_answer`
- 四级风险判定（红/橙/黄/蓝）与处置建议 → `nlu.grade_risk` / `nlu.ADVICE`
- 异常上报流转：橙/红 24h/12h SLA 工单 → `call_service._make_ticket`
- 复诊提醒与随访时段（9:00–11:30 / 15:00–17:30）→ 任务排期 `scheduled_at=9:00`，可在设置中扩展

## 五、改造工作量

- 合并/重写 Python 后端 9 个模块（约 1600 行），前端工作台 1 套（HTML/CSS/JS 约 1900 行）
- 5 个病种方案、25 名脱敏患者、40 名 HIS 患者作为种子数据，启动即自动初始化
- 大模型两处调用：话术生成（方案编辑器）、通话结构化抽取（含 JSON 校验、失败兜底）
